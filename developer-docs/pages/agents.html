Agent Profiles

Persona 与主智能体

MyHarness 把“智能体身份”做成 persona 文件，再在运行时转换成 AgentProfile。它控制系统提示词、可用工具、默认模型、审批模式，以及是否允许创建子智能体。

1. Persona 放在哪里

Persona 和 Skill 共用扫描入口，主要由 harness/skills.py 负责读取。系统会扫描项目级和用户级目录，然后按 front matter 解析。

  • 项目级目录适合和仓库一起提交，例如 .myharness/personas 或项目 Skill 目录中的 persona 类型文件。
  • 用户级目录适合本机私有配置，例如个人 API 偏好、常用角色。
  • 隐藏 persona 可以保留在系统中，但不在前端普通列表展示。

2. AgentProfile 字段

harness/agents.py 中的 AgentProfile 是运行时结构。它不是单纯展示名称，而是会影响 Engine 构造。

字段作用
name / description前端展示和模型选择角色时使用。
system_prompt注入 Prompt 组装层，决定角色工作方式。
allowed_tools限制该智能体能看到和调用的工具集合。
provider / model覆盖会话默认模型配置。
default_approval_mode会话创建时的默认审批策略。
can_spawn决定是否可以调用 spawn_agent。
spawn_allowlist限定它能创建哪些子智能体。

3. 创建会话时如何生效

  1. 前端或 REST 创建 session，传入 persona 名称或 profile id。
  2. api/rest.py 写入 session metadata。
  3. harness/factory.py 读取 metadata，选择 provider、approval mode 和 persona。
  4. 系统提示词组装时把 persona system prompt 放进 PromptBlock。
  5. 工具注册阶段根据 allowed_tools 过滤工具。

4. 当前几个主智能体的定位

当前项目已经从早期占位 persona 逐步转向更通用的角色设计。比较推荐的方向是：

Builder

适合直接实现、修改代码、运行测试、处理可执行任务。权限可以相对完整，但高风险工具仍走审批。

Planner

适合拆解目标、写计划、发现风险、管理待办。可减少写文件和 shell 权限，更多依赖 todo 与 ask_user。

Researcher

适合检索、阅读、归纳材料。工具偏向搜索、读取、web_fetch，默认不写项目文件。

Reviewer

适合代码审查、文档审查、风险分析。它应更多输出 findings，而不是自动修复。

5. 修改建议

新增 persona 时优先写清三个问题：它为谁服务、默认能做什么、什么动作必须审批。这样 AgentProfile 就不会只是一个名字，而是真正成为运行时约束。

注意 persona 的 allowed_tools 只是可见工具范围，最终是否执行仍会经过 ToolExecutor、approval mode、confirm_tools 和 hook。
