Coverage Audit

对照 learn-claude-code 的章节审计

本页以 D:\GitHub\learnHarness\learn-claude-code 的 12 个中文章节为参照，检查 MyHarness 当前实现和文档有没有遗漏、有没有设计不对齐。结论分成四类：已覆盖、部分覆盖、设计不同、缺失。

总览

章节参照主题MyHarness 状态结论

s02Tool Use已覆盖并增强ToolRegistry / ToolExecutor 比 dispatch map 更完整。

s01 Agent Loop

参照仓库强调一个不变循环：发送 messages 和 tools 给模型，遇到 tool_use 执行工具，把 tool_result 放回消息，再继续。

MyHarness 对应实现是 harness/engine/engine.py 的 AgentEngine 和 harness/engine/loop.py 的 ReactLoop。它已经超出最小循环，支持状态机、取消、审批等待、队列、压缩、事件和 WebSocket 推送。

判断 已覆盖。文档里已有“主循环”页，不需要补实现，只需要在汇报时强调循环是所有机制的底座。

s02 Tool Use

参照仓库用 dispatch map 说明“加工具不改循环”。MyHarness 的 ToolRegistry 和 ToolExecutor 就是这个思想的工程化版本。

当前工具层还包含并发执行、hook、审批 gate、结果溢出处理、MCP 工具包装、闭包绑定运行时依赖等能力。

判断 已覆盖并增强。需要继续确认所有文件工具都有路径沙箱和输出截断，尤其是 shell / powershell。

s03 TodoWrite

参照仓库的重点不是“有 todo 工具”这么简单，而是三个约束：多步任务先建计划、同一时间只允许一个 in_progress、连续多轮不更新 todo 时注入提醒。

MyHarness 已有 todo_write、PlanStore、SQLite plans / plan_items、前端 Plan 面板和系统计划提醒。对应文件包括 harness/tools/builtin/todo_tool.py、harness/storage/plan_store.py、harness/factory.py 和 static/index.html。

当前已经补齐两个关键约束：todo_write 会拒绝多个 in_progress；ReactLoop 连续 3 轮工具调用没有更新 todo_write 时，会插入隐藏提醒，要求模型更新可见计划。

判断 基本版已覆盖。后续如果要更强，可以把提醒策略抽成独立 PlanPolicy，并在前端显示“计划过期”状态。

s04 Subagents

参照仓库的 subagent 是临时上下文：运行自己的 messages，最终只给父 agent 返回摘要，子上下文丢弃。

MyHarness 采用更产品化的设计：子 agent 是一个真实 session，有 sub_* id、metadata、parent_session_id、display_name、spawn_depth、可单独打开查看，并可在左侧会话树展示。核心实现在 harness/tools/builtin/spawn_agent.py 和 AgentEngine.register_pending_spawn()。

判断 这是设计不同，不是错误。要在文档里明确：MyHarness 选择“可追踪子会话”，代价是需要前端 session tree 和 pending_spawns 管理。

s05 Skill Loading

参照仓库采用两层知识注入：系统提示里只列 Skill 名称和描述，模型需要时调用 load_skill 读取全文。

MyHarness 对应 harness/skills.py 和 use_skill 工具。它扫描项目级和用户级目录，也兼容 Claude 风格目录。当前文档的 Skill 页已经覆盖“描述注入 + 按需全文加载”。

判断 已覆盖。后续优化重点不是有没有 Skill，而是减少模型过度调用 Skill。

s06 Context Compact

参照仓库有三层：旧 tool_result micro compact、token 阈值触发 auto compact、manual compact 工具，并把完整 transcript 存到磁盘用于恢复。

MyHarness 的 ContextCompressor 已有两层：micro 清理旧 tool result，auto 调 summarizer 摘要旧消息，并强制重注入 system_identity 和 task_goal。这一点比参照仓库更注意身份漂移。

当前已经在 auto compact 前保存完整 transcript，默认路径是 .myharness/transcripts/<session_id>/round_*.jsonl。当前 /compact 仍是 command 系统能力，不等同于模型可调用的 compact tool。

判断 基本版已覆盖。后续可以把 transcript 做成 REST 调试接口，并决定是否提供模型可调用 compact tool。

s07 Task System

参照仓库把 todo 升级为持久任务图：每个 task 有 id、status、blockedBy、owner，完成任务会自动解除依赖。

MyHarness 当前的 TaskRecord 是统一展示模型，不是持久任务图。它合并 plan item、pending command、pending spawn，适合 UI 呈现，但不能表达 DAG、blockedBy、owner、自动解锁。

建议 新增 TaskStore / TaskGraph，保留 TaskRecord 作为 UI projection。不要把 TaskRecord 扩展成所有业务状态，否则会混淆“事实存储”和“展示视图”。

s08 Background Tasks

参照仓库的后台任务是命令级：启动后台线程跑慢命令，完成后把通知队列注入下一轮 LLM。

MyHarness 已新增轻量后台任务工具 background_task，支持 start、status、list、cancel。它适合跑测试、安装、构建这类慢命令，让模型稍后主动查询结果。

判断 轻量版已覆盖。后续可以补前端后台任务面板和“后台完成后自动注入下一轮上下文”。

s09 Agent Teams

参照仓库从这里开始进入长期团队系统：TeamMember 名册、队友生命周期、MessageBus、每个 agent 的 JSONL inbox。

MyHarness 有多 session 和子 agent，但没有持久队友名册，也没有 agent 间邮箱。子 agent 多数仍由父会话通过 spawn 工具直接创建并等待结果。

建议 若要做团队，应新增 TeamStore、TeamMember、MessageEnvelope、MessageBus。session tree 不能完全替代团队模型。

s10 Team Protocols

参照仓库把关机请求和计划审批抽象成 request-response FSM：pending -> approved / rejected。

MyHarness 已有人机审批和 ask_user，但没有 agent-agent 协议审批。现有 approval_mode 面向工具风险，不是队友之间的计划审查。

建议 抽象 ProtocolRequest / ProtocolDecision，可复用给 plan review、shutdown、handoff、merge approval。

s11 Autonomous Agents

参照仓库的自治 agent 会在 IDLE 阶段轮询 inbox 和任务板，自动认领未分配任务，并在压缩后重注入身份。

MyHarness 的子 agent 目前由 spawn 触发，运行到完成后返回；没有 idle polling、自动认领、长期存活工作者。压缩身份重注入在单会话层已做，但没有 teammate identity lifecycle。

建议 自治应建立在 TaskGraph + TeamMember + MessageBus 之上，不建议先写轮询循环，否则会缺少稳定任务来源。

s12 Worktree Task Isolation

参照仓库把任务控制面和执行目录分开：Task 绑定 git worktree，每个任务在独立目录运行，并记录 worktree 生命周期事件。

MyHarness 当前没有 worktree 管理器。shell / powershell 默认仍在同一个 workspace 中执行，因此并行 agent 改同一文件时可能互相污染。

建议 在实现长期团队前，至少设计 WorktreeManager 接口：create、bind_task、run_in_worktree、keep、remove、events。

优先级建议

  1. s03 / s06 / s08 已完成基本版：计划约束、transcript 归档、后台任务工具。
  2. s07 暂缓：当前 PlanStore + TaskRecord 先满足基础 harness，不急着做 TaskGraph。
  3. s09-s12 继续放入未来增强：TeamMember、MessageBus、Protocol FSM、Autonomous worker、WorktreeManager。
