AgentEngine 与 ReAct 主循环

Engine 是一个会话的单一事实源。ReactLoop 是实际执行推理和工具调用的循环。两者分工清楚：Engine 管状态，Loop 管每轮怎么跑。

相关文件

文件职责
harness/engine/engine.py会话状态、消息、队列、审批、question、快照。
harness/engine/loop.pyReAct 循环、模型调用、工具执行、interrupt。
harness/engine/state_machine.py状态枚举和状态转移约束。
harness/factory.py把 provider、工具、压缩器、loop、engine 装配起来。

EngineConfig

EngineConfig 是运行时会话配置，关键字段包括：

  • session_id：当前会话 id。
  • system_prompt：构建后的完整系统提示词。
  • confirm_tools：需要审批的工具集合。
  • provider_name 和 agent_id：当前会话使用的 provider 和 agent profile。
  • spawn_depth：多 Agent 嵌套深度。
  • question_mode：是否允许 ask_user。
  • approval_mode：ask、auto、full。
  • memory_store 和 plan_store：长期记忆和计划存储。

Engine 管理的状态

  • _messages：当前会话的消息列表。
  • _sm：状态机。
  • _pending_tool_calls：等待审批的工具调用。
  • _pending_question_requests：等待用户回答的问题。
  • _pending_commands：运行中继续输入形成的队列。
  • _pending_spawns：正在运行的子 Agent。
  • _event_listeners：WebSocket 使用的事件监听器。

状态机

状态含义
WAITING_INPUT等待用户输入。
RUNNING主循环运行中。
WAITING_CONFIRMATION工具命中审批规则，等待用户允许或拒绝。
WAITING_INTERRUPTask_user 已提出问题，等待用户回答。
COMPLETED当前任务完成。
ERROR运行出错。

send_message 的逻辑

  1. 如果 Engine 正在 RUNNING，新输入不会直接插入 messages，而是进入 pending_commands。
  2. 如果任务看起来复杂，Engine 会尝试插入一条隐藏计划提醒，要求模型使用 todo_write。
  3. 追加用户消息。
  4. 状态转为 RUNNING。
  5. 后台创建任务执行 _run_loop_guarded()。
  6. 顶层 Agent 首次运行时会异步生成标题。

ReactLoop 每轮顺序

  1. 检查 cancel 信号。
  2. 执行上下文压缩。
  3. 读取工具 schema。
  4. 调用 LLM。
  5. 如果没有 tool call，追加 assistant 消息并结束。
  6. 检测重复工具调用，必要时注入 break message。
  7. 进入审批 gate。
  8. 并发执行工具。
  9. 验证 assistant/tool 消息配对。
  10. 原子追加 assistant 和 tool_result。
  11. 如果 tool_result 是 interrupt，暂停到 Engine 层。
  12. 安全点处理 pending command。

为什么要有 pending queue

OpenAI-compatible 工具调用协议要求 assistant 的 tool_call 后面必须紧跟对应 tool_result。如果用户在中间插入新消息，下一次请求可能直接失败。

因此运行中的用户输入会先进入 pending_commands。当前工具链闭合后，Engine 再按顺序处理队列。

快照接口

GET /sessions/{id}/state 调用 engine.get_snapshot()，返回前端需要的状态：

  • 会话状态、是否运行中、错误信息。
  • 最近消息。
  • pending approval、pending question、pending commands、pending spawns。
  • todos 和统一任务视图 tasks。
  • question mode、approval mode、agent id。
