Developer Guide

扩展开发

这一页面向继续开发 MyHarness 的同学，说明新增能力时应该改哪里、怎么验证，以及哪些边界不要绕过。

1. 新增内置工具

  1. 在 harness/tools/builtin 下实现工具函数。
  2. 定义清晰的参数 schema 和返回结构。
  3. 在 ToolRegistry 注册工具。
  4. 根据风险决定是否加入 confirm_tools。
  5. 补充测试，至少覆盖成功、参数错误和审批路径。

2. 新增 Provider

Provider 应实现统一聊天接口，把项目内部 message / tool schema 转成厂商 API 格式，再把返回值转回统一结构。新增 Provider 时要注意流式输出、工具调用格式、错误码和 base_url 配置。

3. 新增 Persona

Persona 不应该只是换一个名字。请同时明确 system prompt、allowed_tools、默认 provider、默认 approval mode、是否允许 spawn，以及适合处理的任务边界。

4. 新增 Skill

Skill 应写成按需加载的能力说明。描述要足够具体，避免模型在无关任务里频繁调用。大型参考资料可以放在 Skill 附带文件中，由 Skill 正文说明何时读取。

5. 新增持久化对象

新增持久化对象时需要同时考虑内存后端、SQLite 后端、REST snapshot 和前端展示。只改 SQLite 容易导致测试环境或前端状态不一致。

6. 新增 Hook

Hook 适合放在不想侵入主循环但需要观察或修改行为的地方，例如工具执行前后、模型调用前后、审批决策、memory 写入和 session 创建。

Hook 点适合做什么
before tool参数审计、风险标记、限流。
after tool记录结果、触发通知、抽取 memory。
before model统计 token、注入额外上下文。
session created自动命名、绑定父子关系、初始化默认状态。

7. 推荐验证清单

  • CLI 是否能跑通同样能力。
  • Web 是否能实时展示状态变化。
  • approval mode 切换后行为是否符合预期。
  • 子智能体是否正确挂到会话树。
  • SQLite 重启后状态是否恢复。
  • 错误路径是否写入 events，前端是否可见。

8. 仍建议继续补的能力

为了把框架推进到更完整的 harness，可以继续完善独立持久 Memory 策略、后台任务完成后的自动上下文注入、TeamMember / MessageEnvelope、任务依赖图、自动结果汇总、worktree 隔离，以及更细粒度的工具权限策略。
